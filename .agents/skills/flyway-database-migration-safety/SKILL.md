# Flyway Database Migration Safety

Treat Flyway as the schema owner. Keep production schema migration, development seed data, application runtime, and deployment execution as separate concerns.

Never apply a migration to production, run destructive database commands, or change database roles without explicit user approval.

## Inspect Before Changing

1. Inspect current files under `recipes-api/src/main/resources/db/migration` and `db/dev-migration`.
2. Inspect affected JPA entities, repositories, application profiles, Maven Flyway config, and migration workflows.
3. Classify the change as production schema, development seed, test-only setup, or deployment configuration.
4. Determine whether persistent databases may already contain existing versioned migrations.
5. For schema changes, create a new migration instead of editing an applied migration.

## Migration Ownership

- Keep production schema migrations in `recipes-api/src/main/resources/db/migration`.
- Name production migrations `V<number>__descriptive_stable_name.sql`.
- Keep development-only seed data in `recipes-api/src/main/resources/db/dev-migration`.
- Name development seed migrations `R__descriptive_stable_name.sql`.
- Accept version gaps. Inspect the current sequence and choose the next safe version; never add filler migrations.
- Never edit an already-applied `V__` migration on a shared or persistent database. Add a corrective migration.
- Never run development migrations in production.
- Never automate `flyway:clean` or `flyway:repair`, and never disable validation to hide a mismatch.

## Development Seed Data

- Make every repeatable `R__` seed migration idempotent because Flyway reruns it after checksum changes.
- Use `INSERT ... ON CONFLICT DO NOTHING` or `DO UPDATE` where appropriate.
- Use deterministic `public_id` values for seeded rows when relationships need stable references.
- Prevent duplicate recipe tags, ingredients, steps, and step-ingredient links.
- Do not depend on unstable row ordering.
- On a local checksum mismatch, reset the disposable local PostgreSQL database or Docker volume instead of repairing Flyway history.

## Production Runtime And Deployment

- Keep `application-prod.yml` with `spring.flyway.enabled=false`.
- Keep production Hibernate schema behavior at `spring.jpa.hibernate.ddl-auto=validate`.
- Run production migrations from CI/CD before triggering Render deployment.
- Use only `classpath:db/migration` for production Flyway commands. Never include `classpath:db/dev-migration`.
- Run `mvn process-resources` before Maven Flyway commands that consume classpath migrations.
- Do not connect ordinary pull-request CI to the real production database.
- Use the manual `Inspect Production Migrations` workflow for production `flyway:info` and `flyway:validate`.
- Prefer a dedicated migration role and a lower-privilege runtime role, but change roles only with explicit approval.

## Neon Connection Safety

- Use a direct, non-`-pooler` Neon endpoint for migrations and migration inspection.
- Require `sslmode=verify-full` for production migration JDBC URLs; do not weaken it unless explicitly requested.
- Install the Let's Encrypt ISRG Root X1 certificate before GitHub Actions connects with JDBC `verify-full`:

```bash
mkdir -p ~/.postgresql
curl -fsSL https://letsencrypt.org/certs/isrgrootx1.pem -o ~/.postgresql/root.crt
chmod 600 ~/.postgresql/root.crt
```

- Treat live Neon state as unverified until an explicit connection, inspection, or migration succeeds.

## Design Safe Schema Changes

Prefer expand/contract deployments:

1. Add compatible nullable columns, tables, or indexes.
2. Deploy code that can operate with the expanded schema.
3. Backfill separately when needed.
4. Add constraints or remove obsolete schema in a later migration.

Avoid:

- Dropping or renaming schema still used by the deployed application.
- Adding `NOT NULL` columns without a safe default or backfill plan.
- Long blocking rewrites without considering table size and lock behavior.
- Destructive data changes without explicit confirmation.
- Casual changes to `public_id` semantics. Internal IDs remain UUIDs; API-facing IDs remain `public_id` values generated by Java.

## Verify After Changing

Verify migrations and entity mappings against PostgreSQL, not H2:

```bash
cd recipes-api
mvn clean verify
```

Use a clean Maven lifecycle after migration or resource-path changes so stale files under `target/classes` cannot hide problems. If the sandbox blocks Maven cache writes, rerun where `~/.m2` is writable and report that environment limitation accurately.

Then confirm:

- Production/default/CI Flyway locations exclude `db/dev-migration`.
- The development profile includes both schema and development seed locations.
- Production app startup does not run Flyway and still validates Hibernate mappings.
- Each JPA schema change has a matching new migration.
- Migration SQL and entity mappings agree.
- No production database operation was performed without explicit approval.

## Review Checklist

Flag:

- Edited applied `V__` migrations.
- Development seed data stored in versioned production migrations.
- Non-idempotent repeatable seed migrations.
- Production startup migrations or production inclusion of `db/dev-migration`.
- Automated Flyway clean, repair, or disabled validation.
- Entity schema changes without a migration.
- Migration/entity mismatches or H2-only verification.
- Pooled Neon migration URLs or weakened production SSL.
- Unsafe destructive or blocking migrations.
